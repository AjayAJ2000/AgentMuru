# AgentMuru 0.3 Clean MVP Release Design

## Decision

AgentMuru 0.3 will ship as a Python-first MVP. The supported product is the Python runtime,
FastAPI server, browser Workspace, SQLite persistence, governed tools, and optional official
model-provider adapters. The Go terminal runtime remains available under a clearly labeled
Labs section and is not presented as an alternative installation path on the home page.

This design extends the approved
`2026-08-16-agentmuru-popular-model-sdk-providers-design.md` specification. That specification
remains authoritative for provider message normalization, persistence, errors, security, and
contract testing.

## Release Outcome

A new user can install AgentMuru, generate a starter, run it without credentials, inspect the
result in Muru Workspace, and then switch the same application to OpenAI, Anthropic, or Google
by installing one optional extra and setting the provider's standard environment variable.

The repository, documentation site, GitHub project, release page, and PyPI page all describe
that same product. Active surfaces contain no BrickFlowUI naming or obsolete component-framework
instructions. Immutable git and package history is not rewritten.

## Product Boundary

### Supported MVP

- Python 3.10 through 3.13.
- Provider-neutral agents, tools, sessions, events, approvals, artifacts, workflows, and traces.
- Credential-free `FakeModel` starter.
- Optional OpenAI, Anthropic, and Google Gen AI adapters using official async SDKs.
- SQLite durability for a single active Runtime process per database.
- FastAPI HTTP/WebSocket protocol and the browser-based Muru Workspace.
- Databricks adapters with claims limited to the evidence recorded in integration status.

### Labs

- Native Go terminal workspace.
- Local llama runtime installation and supervision.
- Agent-pack compiler and measured action-router fixture.

Labs pages state their release artifact, supported operating systems, evidence level, and known
limitations. Labs content is absent from the primary quickstart and PyPI installation story.

### Not in the MVP

- PostgreSQL persistence.
- Multi-process writes to one SQLite database.
- Hosted tools that bypass AgentMuru governance.
- Provider-managed web search, code execution, or MCP.
- Android builds, automatic model selection, and production claims for unqualified local models.

## User Journey

The primary journey is linear and executable:

1. Install `agentmuru==0.3.0` and run `muru doctor`.
2. Run `muru init hello-muru --name "Hello Muru"`.
3. Start `muru run app:application` and open Muru Workspace.
4. Submit a prompt to the deterministic starter and inspect the ordered run history.
5. Add a governed tool and observe permission and approval behavior.
6. Persist the application with SQLite and reopen the session.
7. Optionally install one provider extra and replace `FakeModel` without changing the Runtime.

Every command and code sample used in this journey is covered by a documentation contract,
example test, clean-wheel scenario, or browser test.

## Runtime and Provider Changes

The 0.3 provider work follows the existing provider design. The release adds:

- optional `openai`, `anthropic`, `google`, and aggregate `providers` extras;
- official-SDK adapters under `agentmuru.integrations`;
- normalized assistant tool-call records persisted in session messages;
- additive SQLite migration and HTTP/frontend protocol support for tool-call records;
- deterministic provider contract fixtures for text, streaming, tools, usage, errors, and
  cancellation;
- safe public provider error codes with no raw SDK objects or exceptions in persistent state;
- executable provider examples and opt-in credential checks; and
- a provider-aware scaffold option while keeping `FakeModel` as the default.

Provider packages remain outside core dependency direction. Importing the base `agentmuru`
package never imports a vendor SDK.

## Documentation Architecture

The public MkDocs site is rebuilt around user tasks:

- **Get started**: installation, five-minute starter, Workspace tour, and real-model setup.
- **Build**: agents, models, tools, approvals, sessions, artifacts, workflows, and handoffs.
- **Providers**: provider selection plus focused OpenAI, Anthropic, and Google guides.
- **Operate**: server, persistence, security, observability, deployment, and Databricks.
- **Reference**: CLI, Python API, event protocol, configuration, capability matrix, and release
  notes.
- **Labs**: native terminal, local models, and agent packs with explicit preview boundaries.
- **Project**: roadmap, contributing, support, and security links.

Thin concept stubs are replaced with explanations that define the abstraction, show a complete
example, describe lifecycle and failure behavior, and link to the exact reference. Internal
planning documents are excluded from the generated site. Pre-AgentMuru migration pages,
transformation logs, old architecture snapshots, and obsolete roadmap sections are removed from
the public documentation tree.

## Documentation Presentation

Material for MkDocs remains the generator to avoid a site-framework migration during the MVP.
The theme receives a focused AgentMuru treatment:

- a compact product header with visible version and GitHub links;
- a restrained dark-teal visual system with accessible contrast and system fonts;
- a home page that leads with one install command and one runnable outcome;
- clear stable, beta, and Labs status badges;
- code-copy support, content tabs, annotations, search, section navigation, and previous/next
  navigation;
- responsive task cards and capability tables without decorative dashboard styling; and
- a footer with support, security, PyPI, repository, and license links.

The site is verified at desktop and mobile widths, with keyboard navigation, visible focus,
reduced-motion support, and no third-party font request.

## Repository and GitHub Organization

The repository root keeps only public product, development, security, and release information.
GitHub templates use AgentMuru vocabulary and the actual verification commands. Hidden planning
material remains excluded from the docs build.

Remote cleanup is performed only after identifying exact merged or obsolete targets:

- delete merged pre-AgentMuru working branches and superseded Dependabot branches;
- close duplicate dependency PRs once the grouped update is verified;
- retain AgentMuru releases and remove obsolete BrickFlowUI release entries and matching tags
  from the active repository release surface;
- keep `main` protected and make it the only long-lived development branch;
- disable the unused wiki and downloads surfaces; and
- preserve immutable git commit history rather than force-rewriting the repository.

GitHub Projects gains one `AgentMuru 0.3 MVP` project with Backlog, Ready, In progress, In review,
and Done states. Existing roadmap issues are triaged into the board, a 0.3.0 milestone is applied
to release work, and future items remain in Backlog with evidence-based labels.

## PyPI and Release Surfaces

Version `0.3.0` is the first polished AgentMuru MVP release. Package metadata, README, wheel,
sdist, docs, and GitHub release use the same description, Python support range, optional extras,
and URLs. The scaffold pins a compatible `0.3` range rather than the obsolete `>=0.1.0` floor.

PyPI is updated through the existing trusted-publishing workflow after the qualified GitHub
release is published. The release is promoted only if wheel installation, provider-extra
installation, package-content inspection, README rendering, and `twine check` pass.

## Error Handling and Security

- Documentation distinguishes unsupported behavior from errors and does not advertise planned
  work as shipped.
- Provider authentication, permission, rate-limit, timeout, invalid-request, unavailability,
  malformed-tool, and generic failures use stable safe codes.
- Raw credentials, request bodies, provider responses, unredacted sensitive tool arguments, and
  exception details never enter messages, events, traces, logs, examples, fixtures, or docs.
- The server guide requires explicit trusted hosts/origins, TLS termination, session ownership,
  database permissions, backup, and tool sandboxing for production deployment.
- SQLite limitations remain prominent wherever durability is presented.

## Verification

The release gate is:

1. Python tests across 3.10, 3.11, 3.12, and 3.13.
2. Ruff and MyPy.
3. Frontend unit tests, lint, type check, production build, and bundle budgets.
4. Chromium end-to-end checks for starter, approvals, persistence, and reconnect.
5. Go tests, vet, build, and action-router fixture for Labs.
6. Strict MkDocs build plus internal-link, stale-term, and sample-contract checks.
7. Wheel and sdist build, `twine check`, clean base install, and independent provider-extra
   installs.
8. Deterministic provider contract tests and explicit records for run or skipped credential
   checks.
9. A final scan of repository, docs output, package metadata, GitHub surfaces, and PyPI for
   conflicting versions or legacy product naming.

Local test runs use a repository-owned pytest base directory on restricted Windows environments;
the initial 32 setup errors were caused by denied access to the global pytest temp directory, not
by product failures.

## Definition of Done

The work is complete when a fresh user can follow the primary journey from PyPI to a running
Workspace, switch to any supported provider using a documented optional extra, and understand
the runtime without reading source code. All release gates pass, public docs contain no legacy
product references, Labs is visibly separated, GitHub project and issue state match the release,
obsolete active GitHub surfaces are cleaned, and PyPI shows the qualified 0.3.0 package.
